# Backup, restore and component releases

**System → Backup** creates an archive with the `/etc/aios` configuration, the database (through the SQLite backup API), users, session metadata, the registry and the Open WebUI data. The chat is stopped during the copy so its own database stays consistent. GGUF weights are excluded unless you ask for them. The control plane stays available throughout. Archives are `0600`, reachable through the API only by a SUPERADMIN, and they contain secrets.

To restore, upload the archive and confirm the operation. The broker extracts it into a staging area with limits, refuses traversal, links and device nodes, and verifies the SQLite integrity and schema. It stops the services that write data, keeps a pre-restore copy in `backups/pre-restore-TIMESTAMP`, replaces configuration, database and chat data, then restarts. Sessions are revoked. If the GGUF files are missing, those models become DISABLED and unpublished: install them again or restore the matching weights. The archive does not replace the operating system or files outside the paths it owns.

Do not power off during a restore. If the process is interrupted, use the physical console and the pre-restore copy to put the database, configuration and chat directories back with the services stopped, fix ownership (`aios` for database and configuration, `aios-webui` for the chat) and start the services again. Always keep a copy somewhere else: backups and models on the same disk do not survive that disk failing.

## Daily backups

The **Schedule** form in **System → Backup** makes a backup every day at the chosen hour (appliance time zone) and keeps the newest *N* of them. The schedule removes only the backups it made; backups made by hand and uploaded archives stay until you delete them. Each archive is listed with its date, size and how it was made (**SCHEDULED**, **UPLOADED**), and whether it includes the model weights.

## Encryption

A backup holds the accounts, the credentials and the chat history. Set a **passphrase** of at least 12 characters and every backup from then on is sealed with AES-256-GCM under a key derived from it with scrypt; the unencrypted archive never stays on the disk. Sealed archives end in `.tar.gz.enc` and are marked **ENCRYPTED**. The file is sealed in 4 MiB chunks, each bound to its position, so an archive that is altered, reordered or cut short is refused instead of restored.

Restoring a sealed archive uses the passphrase you type in the restore dialog, or the one this appliance is set with when the field is left empty. That is how a backup moves to a new appliance: upload the `.enc` file there and give its passphrase. Changing or removing the passphrase does not re-encrypt earlier archives: they keep the passphrase they were made with, so note it somewhere safe. Without it an encrypted backup cannot be opened by anyone, including AIOS.

## Component releases

Component releases use a canonical JSON manifest (sorted keys, `,` and `:` separators) with `component`, `version` and `sha256`, signed with Ed25519. The accepted components are `application`, `runtime` (llama.cpp), `imaging` (stable-diffusion.cpp), `voice` (whisper.cpp), `open-webui` and the optional `cuda` package ([GPU acceleration](gpu.md#cuda-for-nvidia-cards-optional)), and the archive carries the contents of the matching directory under `/opt/aios`. After an application release, the control plane adds any repository the new release ships, disabled like the others, and the release's systemd units, NGINX site, firewall rules and chat stylesheet are installed with it: each file that changed is checked by the tool that reads it (`nginx -t`, `nft -c`) and put back as it was if the check fails, and units the release adds are enabled. The same happens at every boot, and a rollback puts back the files of the release it restores. The system stops the affected services, keeps a `.previous` copy, applies the release and checks the services; a failure restores the previous directory. An update must match the same Python/OS ABI: a virtualenv built for another path or distribution will not work.

Component releases are applied from **System → Updates → Application updates**, or through the API (`POST /api/v1/aios/system/update`). The appliance ships with no trust anchor: install the Ed25519 **public** key of whoever signs your releases first, by pasting it in that page (it is stored at `/var/lib/aios/system/release.pub`); without a key every update is refused. `scripts/sign-release.py` creates the signed manifest on the machine that holds the private key, which never touches the appliance. A release is accepted only if its checksum matches the manifest, the signature verifies, the archive is safe, the services come back and the component answers its health endpoint again; otherwise the previous directory is put back. The build info and the image checksum can be part of a release signed by whoever distributes it.

Operating system updates: the appliance checks the Ubuntu archive shortly after boot and every day. **System → Updates** in the portal shows the result (packages available, how many are security fixes, whether a restart is pending) with *Check now* and *Install updates*; the console menu does the same. Installing is a SUPERADMIN action and runs the same script as the console. Platform upgrades (a new AIOS image) are done by reinstalling from a verified image and restoring a backup; there is no A/B layout. Keep the old disk, or a verified clone, to roll the platform back. Model updates are separate installations or revisions, and never automatic.
