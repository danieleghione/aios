# Troubleshooting

**No address on the console**: run `ip -br address`, check the cable, DHCP and `networkctl status`. The portal always uses HTTPS; the browser warns about the initial self-signed certificate. Use the physical console for the fingerprint and the network configuration.

**Boot without a root filesystem**: check `boot/grub/grub.cfg`, the UUIDs in fstab and the presence of `boot/initrd.img-*`; under UEFI also the ESP, under legacy BIOS the BIOS boot partition with GRUB's core.img. The build creates the initramfs explicitly and the QEMU test stops on a kernel panic.

**A service is unavailable**: from the console, look at the network and services entry, or `journalctl -u aios-control-plane -n 100` on a machine where you have a shell. An offline repository or a failed runtime must never restart the system. `systemctl reset-failed NAME` followed by a restart retries a service that hit its start limit.

**Open WebUI on first start**: database migrations and module imports can take a few minutes on a slow VM. The chat account is the AIOS account: if `https://IP/` redirects to the portal, the session is missing or expired. A 500 when opening the chat means the control plane is not answering the identity check. If a model is published but not running, the API answers 409: start it from the Runtime page. The context can exceed RAM even for a fairly small GGUF file.

**CPU at 100% around an answer**: inference uses every core while the model generates, and a reasoning model (Qwen3.5/3.8, DeepSeek R1, Magistral) produces hundreds or thousands of thinking tokens before the answer; when generation ends llama-server goes idle. By default Open WebUI also uses the same model for automatic tasks: chat title, tags, follow-up questions, query rewriting. AIOS sets them up on first boot as follows: the title is generated with reasoning switched off (a few seconds), tags, follow-ups and query generation are disabled, and the built-in tools are disabled (they added about 6000 tokens of schemas to every request and exceeded a default 4096 context). These are defaults: settings an administrator saves in Open WebUI (Admin panel → Settings → Interface, and Models) take precedence. To shorten the answers of a reasoning model, lower **Reasoning budget** in the runtime configuration (0 disables it) or send `"chat_template_kwargs": {"enable_thinking": false}` in the API request.

**The GPU is not used**: open **Hardware → GPU acceleration**. If the GPU is missing, the system has no Vulkan driver for it: in a VM, check that the card is passed through (an emulated display adapter does not count); for NVIDIA, a driver that failed to load is reported under the list — Kepler (GTX 600/700) and older cards are not supported by the current NVIDIA driver and are tried with nouveau, which may not offer compute. The list is probed two minutes after boot and then every ten minutes, and again before every model start. If the GPU is listed but the Runtime page says *Running on the CPU* with a note, the GPU start failed and the model was started on the CPU instead: the note carries the llama.cpp error, most often not enough video memory for the context. Lower the context, or choose **GPU only** to get the failure instead of the fallback. More in [GPU acceleration](gpu.md).

**"image input is not supported" in the chat**: the model has no vision projector loaded. If it is a vision model, synchronise its repository, press **Add image input** under **Installed models**, wait for the download, then restart the model. If the model is text-only (no *IMAGE INPUT* badge in the catalogue), it cannot read images: choose a vision model such as Qwen-VL or Gemma 3.

**Pictures are refused or never arrive**: the chat's image button and `/v1/images/generations` need a diffusion model that is installed *and published*; without one the answer says so. A picture is slow, not stuck: without a GPU, 512×512 with 20 steps takes minutes, and the gateway waits up to 30 minutes before giving up. The quickest check is **Generate a picture** under Installed models, which shows the time each attempt took; the runtime log of the image model carries the engine's own errors. See [image generation](image-generation.md).

**A download failed**: check the licence or gating, the repository, the token, TLS, disk space and the state under Downloads. Temporary HTTP errors are retried with backoff up to five times. A wrong SHA256 or an invalid GGUF structure deletes the partial file and marks it FAILED. Pause keeps the `.part` file; cancel removes it. Never edit the database by hand while the worker writes.

**A model was refused**: read the runtime log. GGUF is a container, not a guarantee that the architecture is supported. Lower context or batch, use a smaller quantisation, or stop other workloads. The runtime does not force swap as a normal strategy.

**The bootstrap code expired**: regenerate it from the console menu, which works only while no administrator exists. **Administrator password lost**: there is no remote reset. Restore a backup taken when the password was known, or reinstall the appliance; the physical console does not offer a shell by design.

**The disk is full**: stop downloads and runtimes and remove models you do not need from the portal. Always keep room for the journal, the database and backups. To grow a VM, enlarge the disk in the hypervisor and reboot: the data partition grows, root stays fixed.

**A build was interrupted**: before removing the rootfs, check mounts with `findmnt`. Unmount any leftover bind mounts; never `rm -rf` a directory that still has `/dev` or `/proc` mounted. Build logs are in `build/`, image test results in `dist/`.
